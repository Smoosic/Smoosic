# Phase 0 Research: Vue-Based Music Library Dialog

All unknowns below were resolved by reading the existing codebase (no external research was needed — this is an internal migration reusing established in-repo patterns, plus one substantively new piece: a general-purpose recursive Vue tree component, which has no prior precedent in this repo). No `NEEDS CLARIFICATION` markers remain in the Technical Context.

## 1. Creation-function pattern must be async, unlike every prior `*Vue.ts` precedent

- **Finding**: Every existing converted dialog's creation function (`SuiLyricDialogVue`, `SuiChordChangeDialogVue`, etc.) is a synchronous `(parameters: SuiDialogParams) => void` that calls `InstallDialog(...)` immediately, mounting the Vue app right away. The legacy library dialog is different: `SuiLibraryDialog.createAndDisplay` (`src/ui/dialogs/library.ts`) is itself `async` and does `await adapter.initialize()` — which awaits `topLib.load()`, an XHR fetch of the top-level library JSON — *before* constructing and displaying the dialog at all. Its call site, `src/ui/buttons/ribbon.ts`'s `executeButtonModal`, already special-cases it: `if (buttonData.ctor === 'SuiLibraryDialog') { await SuiLibraryDialog.createAndDisplay(params, this.config); }` (as opposed to the synchronous `SuiTempoDialogVue(params)` call in the `else` branch for every other modal-button dialog).
- **Decision**: `SuiLibraryDialogVue` is `async (parameters: SuiDialogParams, config: SmoUiConfiguration) => Promise<void>`. It constructs the root `SmoLibrary` from `config.libraryUrl` (identical to `SuiLibraryAdapter`'s constructor), `await`s its `load()`, wraps the now-populated root in Vue's `reactive()`, and only then calls `InstallDialog({...})` — so the dialog is not mounted into the DOM until the top-level library data is ready, matching current behavior exactly (no dialog/tree is visible before that fetch resolves; no loading spinner is introduced, per the spec's Assumptions).
- **Rationale**: Preserves the current user-visible sequencing (nothing appears until the top-level library is loaded) without inventing a loading-state UI the feature description and spec don't ask for.
- **Alternatives considered**: Mounting the dialog immediately with an empty tree and populating it reactively once the fetch resolves — rejected; it would change current behavior (today, nothing is displayed at all until the fetch completes) and would require a spec change (a loading indicator) that wasn't requested.

## 2. `dialogElements` mapping — a single control

- **Finding**: `SuiLibraryDialog.dialogElements` (`src/ui/dialogs/library.ts`) defines exactly one element: `{ smoName: 'smoLibrary', control: 'SuiTreeComponent', label: 'Selection', options: [...] }`. There is no Font, Verse, Ordinality, etc. — just the tree.
- **Decision**: `library.vue` renders exactly one control area: the tree (rooted at a `treeNode.vue` for each of the root `SmoLibrary`'s direct children), inside `dialogContainer.vue`. No dialog-mode/edit-mode split (unlike the lyric/chord dialogs) is needed — this dialog has only ever had one mode.
- **Rationale**: Directly matches FR-002; there is nothing else in the legacy dialog to port.
- **Alternatives considered**: None — the control set is fully specified by `dialogElements` and is trivially a single element.

## 3. No existing recursive/nested-list Vue component — design a new one, recursing directly over `SmoLibrary.children`

- **Finding**: No self-referencing (recursive) Vue component exists anywhere in `src/ui/components/dialogs/*.vue` today. The legacy `SuiTreeComponent` (`src/ui/dialogs/components/tree.ts`) does not work against a nested structure directly either — it flattens the whole tree into `options: TreeComponentOption[]` (each carrying a `parent` URL string) and reconstructs parent→children relationships on every render via `getNodesWithParent`/`calculateOptionTree` (a `Record<parent, children[]>` index), because the legacy dialog framework's `SuiComponentBase` machinery is built around flat, JSON-serializable "options" arrays shared by every dropdown-like control (see `DialogDefinitionOption` in `src/ui/dialogs/components/baseComponent.ts`).
- **Decision**: `treeNode.vue` is a new general-purpose recursive component that instead recurses directly over the real nested structure — one `treeNode.vue` per `SmoLibrary`, rendering a `<treeNode>` for each entry in `props.node.children` when expanded. `library.vue` renders the root level the same way (one `treeNode.vue` per `topLib.children[i]`).
- **Rationale**: `SmoLibrary` is already a nested tree (`children: SmoLibrary[]`); reconstructing a flat parent-pointer array from it (as the legacy component does, for compatibility with the shared dropdown-style component framework it belongs to) would be pure, unnecessary indirection for a component that isn't part of that shared framework. Recursing over the real structure is simpler, avoids re-deriving `getNodesWithParent`-style lookups on every change, and is the idiomatic Vue pattern for tree UIs.
- **Alternatives considered**: Porting the legacy flat-options-array model verbatim (a single non-recursive component walking a flattened list with a `parent` field) — rejected as needless complexity with no benefit here, since this new component has no obligation to fit the legacy `SuiComponentBase`/`DialogDefinitionOption` framework the flat model exists to serve.

## 4. Reactivity: wrap the fetched root in `reactive()`; `SmoLibrary.load()` needs no changes

- **Finding**: `SmoLibrary.load()`/`initialize()` (`src/ui/fileio/library.ts`) mutate an existing instance in place — `initialize()` sets `this.format`, populates `this.metadata`, and reassigns `this.children = []` followed by pushing newly-constructed `SmoLibrary` children; `this.loaded = true` is set by `load()` once `initialize()` returns. None of this replaces the top-level object itself.
- **Decision**: `SuiLibraryDialogVue` wraps the fetched root in Vue's `reactive()` (`const topLib = reactive(new SmoLibrary({ url: config.libraryUrl }))`, then `await topLib.load()` — reactive wrapping first so the in-place mutations during `load()` are tracked) and passes it to `library.vue` as a prop. Because Vue 3's `reactive()` deep-proxies nested objects and arrays (including array reassignment and newly-pushed objects), a folder's lazy `node.load()` — called on a node reached via `topLib.children[i].children[j]...`, itself already part of the reactive tree — automatically triggers re-render of just that folder's newly-populated `children` with zero changes to `SmoLibrary` itself.
- **Rationale**: Directly satisfies FR-006 (fetch on first selection, reflected in the tree) with no modification to the existing, unit-agnostic `SmoLibrary` model (keeping data/UI concerns separated, matching the spirit of Constitution Principle #4), and no manual "force re-render" bookkeeping.
- **Alternatives considered**: Cloning/rebuilding a parallel reactive tree structure on every load (mirroring `SmoLibrary` into a separate Vue-owned shape) — rejected as unnecessary duplication; `reactive()`'s deep-proxy behavior makes the existing class directly usable.

## 5. Selection and expansion state: centralized in `library.vue`, drilled down via callback props

- **Finding**: The established convention for reusable dialog controls in this codebase (`select.vue`) is a `changeCb: (value) => void` prop the component invokes on user interaction, rather than emitting a Vue event the parent listens for. This matters more than usual for a *recursive* component: a plain `emit` from a deeply-nested `treeNode.vue` does not automatically reach `library.vue` — each intermediate level would have to explicitly re-listen and re-emit, once per level, to bubble it up.
- **Decision**: `library.vue` owns all tree-wide state — `selectedUrl: Ref<string>` (which entry is currently selected) and `expanded: Reactive<Record<string, boolean>>` (which folder URLs are currently expanded) — and passes two callback props down through every level of `treeNode.vue`: `selectCb: (node: SmoLibrary) => void` and `toggleCb: (node: SmoLibrary) => void`. Each `treeNode.vue` invokes the callback it was given directly (on the node the user interacted with) and forwards the *same* callback references down to its own child `treeNode.vue` instances — no re-emitting is needed at any level, since the callback is a plain function reference, not a scoped event.
- **Rationale**: Avoids N-level emit-bubbling boilerplate entirely, matches the existing `changeCb` convention this codebase already uses for comparable "leaf reports up to parent" controls, and keeps `treeNode.vue` itself stateless/presentational (all decisions — fetch-or-not, auto-expand, enable Load — live in one place, `library.vue`, making the state machine easy to reason about and test against the spec's acceptance scenarios).
- **Alternatives considered**: `provide`/`inject` for the callbacks — rejected as an unnecessary indirection for two simple function props that are already trivial to pass down explicitly; explicit props keep the data flow visible in the template, consistent with this codebase's existing style (no other dialog component uses `provide`/`inject`).

## 6. Load-control gating reuses `dialogContainer.vue`'s existing `enable` prop — no new dialog-shell work

- **Finding**: `dialogContainer.vue` already accepts an optional `enable?: Boolean` prop (defaulting to `true` via `ref(true)` if omitted) and passes it straight through to `dialogButtons.vue`, which binds it to the OK button's `disabled` attribute (`:disabled="!enable"`). No prior dialog has needed to actually pass a *non-default* value for this prop (lyric/chord dialogs always leave OK enabled), but the mechanism already exists and is exactly what FR-009/FR-010 need.
- **Decision**: `library.vue` computes `canLoad = computed(() => selectedNode.value !== null && selectedNode.value.format !== 'library')` and passes `:enable="canLoad"` to `dialogContainer.vue`. No changes to `dialogContainer.vue` or `dialogButtons.vue` are needed.
- **Rationale**: Directly satisfies FR-009/FR-010/SC-003 using an already-proven, already-tested mechanism, with zero risk of regressing the OK-button behavior of any other already-migrated dialog.
- **Alternatives considered**: Disabling the Load control from within `library.vue`'s own markup (a locally-styled button instead of `dialogContainer.vue`'s shared one) — rejected; it would duplicate the OK/Cancel button styling and layout `dialogContainer.vue`/`dialogButtons.vue` already provide for every other migrated dialog, for no benefit.

## 7. Visual parity: reuse the existing `tree.css` classes and icon set as-is

- **Finding**: `src/styles/tree.css` already defines every class the legacy dialog's rendering needs for the intended look: `ul.tree`/`ul.tree li` (structure/indentation), `li.selected > a` (selection highlight), `li.collapsed ul { display: none }` (collapse mechanism), `button.expander(.expanded|.collapsed)` (expand/collapse affordance, hidden unless one of those two classes is present), and `span.file-type` (icon spacing) — alongside `icon-book`/`icon-file-music` (folder vs. song) and `icon-plus`/`icon-minus` (collapsed vs. expanded) from the existing icon font (`src/styles/fonts.css`). None of this is specific to the legacy jQuery-driven DOM construction in `tree.ts` — it is plain CSS keyed off class names and DOM nesting.
- **Decision**: `treeNode.vue`'s template emits the same class names and nesting shape (`<ul class="tree tree-root">` at the root in `library.vue`, `<li class="tree-branch" :class="{ selected, collapsed: !isExpanded }">`, a `<button class="expander">` with `expanded`/`collapsed`/`icon-plus`/`icon-minus` classes bound reactively, an `<a class="tree-link">`, and a `<span class="file-type">` with `icon-book`/`icon-file-music` bound off `node.format`), reusing `tree.css`/`fonts.css` unmodified.
- **Rationale**: Directly satisfies FR-004 and preserves the current visual appearance with no new CSS, minimizing risk and effort for a purely internal migration.
- **Alternatives considered**: Writing new component-scoped CSS mirroring the same look — rejected as unnecessary duplication of styling that already exists and is already correct.

## 8. Call sites remain untouched; wiring callers over is a separate, later change

- **Finding**: `SuiLibraryDialog.createAndDisplay` is referenced from exactly one place, `src/ui/buttons/ribbon.ts`'s `executeButtonModal` (via the `SuiModalButtonStrings`/`isModalButtonType` special-casing already described in §1), which is in turn reached from ribbon button definitions in `src/ui/ribbonLayout/default/defaultRibbon.ts` and `src/ui/ribbonLayout/default/tabletRibbon.ts` (both configure a button with `ctor: 'SuiLibraryDialog'`).
- **Decision**: None of these files are modified by this feature. `SuiLibraryDialogVue` is net-new and additive, exactly like `SuiLyricDialogVue`/`SuiChordChangeDialogVue` were when first introduced (`010`, `013`) — nothing currently constructing `SuiLibraryDialog` is changed to call it.
- **Rationale**: Matches the spec's Assumptions and the established incremental-migration pattern already used twice in this repo; keeps this feature's blast radius limited to new files only.
- **Alternatives considered**: Also updating `ribbon.ts`'s special case to call the new Vue creation function — rejected as out of scope per the spec's Assumptions; that wiring (and its own manual regression pass against the legacy dialog) is deliberately deferred to a later change.

## 9. Config is passed as a second argument, mirroring the legacy two-argument `createAndDisplay(parameters, config)` shape

- **Finding**: `SuiDialogParams` (`src/ui/dialogs/dialog.ts`) has an *optional* `config?: SmoUiConfiguration` field, but the legacy call site does not rely on it — `ribbon.ts` calls `SuiLibraryDialog.createAndDisplay(params, this.config)` with `config` as a distinct second argument, and `SuiLibraryAdapter`'s constructor likewise takes `(view, config)` as two separate parameters, not one merged object.
- **Decision**: `SuiLibraryDialogVue` takes the same two-argument shape — `(parameters: SuiDialogParams, config: SmoUiConfiguration) => Promise<void>` — rather than relying on `parameters.config`, so that a future caller-wiring change can swap `SuiLibraryDialog.createAndDisplay(params, this.config)` for `SuiLibraryDialogVue(params, this.config)` with a purely mechanical, minimal-diff substitution.
- **Rationale**: Minimizes friction for the (separate, out-of-scope) later step of wiring `ribbon.ts` over to this function, and avoids introducing a dependency on `SuiDialogParams.config` being populated (it is optional and not guaranteed set by every caller).
- **Alternatives considered**: Reading `parameters.config` instead, falling back if unset — rejected; it would diverge from the legacy call site's actual shape for no benefit, and would need a fallback/error path for the unset case that the legacy code never had to handle.
