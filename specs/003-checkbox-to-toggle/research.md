# Phase 0 Research: Dialog Checkbox-to-Toggle Migration

The feature spec left no `[NEEDS CLARIFICATION]` markers, so this phase focuses on confirming the mechanism the user specified (`toggle.vue`, label relocation, combined column width) is well-defined against the actual code, and on resolving the handful of layout variations found across the 11 target files that the spec's "immediately following label div" description doesn't literally cover.

## Decision: Use `toggle.vue` as-is, unmodified

**Rationale**: `toggle.vue` (`src/ui/components/dialogs/toggle.vue`) already implements exactly the on/off switch behavior requested: it takes `domId`, `label`, `initialValue`, optional `disabled`, and a `changeCb(value: boolean)` callback, renders a `.tgl-row` (flex row: knob + label + on/off hint), and is already consumed successfully by `measureFormat.vue` for the same kind of boolean dialog settings this feature targets (e.g. "Break system before measure", "Pad All In System"). No new component or prop is needed.

**Alternatives considered**: Modifying `toggle.vue` to accept a `v-model` directly instead of `initialValue`/`changeCb` was considered for ergonomics, but rejected — the spec requires no behavior change to the toggle control itself (only which dialogs use it), and every current call site already follows the `initialValue` + `changeCb` convention, so changing it would be an unrequested, unnecessary ripple across `measureFormat.vue` too.

## Decision: Map "checkbox column + label column" pairs to Bootstrap's 12-unit grid

**Rationale**: All 11 target files use the project's Bootstrap-based `.row` / `.col col-N` grid (`N` from 1–12) for layout, not flex/CSS-grid custom widths. Every checkbox-plus-adjacent-label pair found is two sibling `col col-N` divs inside the same `.row` (e.g. `col-2` + `col-6` in `addMeasures.vue`, `col-1` + `col-5` repeated twice per row in `scorePreferences.vue`, `col-7` + `col-5` in `viewStaves.vue`). "Update the column width to be the combined width" therefore means: delete the label's `col col-N2` div, and change the toggle's wrapping div from `col col-N1` to `col col-(N1+N2)`, keeping any other modifier classes (`text-start`, `pe-0`, `ms-n4`, etc.) that governed alignment/spacing on the checkbox's column, since the toggle itself renders its own label inline and no longer needs a second column.

**Alternatives considered**: Wrapping the toggle in a full-width `col-12` regardless of the original pair's width was rejected — it would change row layout (e.g. `scorePreferences.vue` packs two checkbox+label pairs per row; collapsing both to `col-12` would stack them vertically instead of side-by-side, violating FR-004/SC-004's "no layout shift" requirement).

## Decision: Only merge columns when the label is genuinely a separate, dedicated sibling column

**Rationale**: Inspecting all 26 checkbox instances shows three distinct markup shapes, and the spec's "div with the label following the input control" wording only cleanly matches the first:

1. **Separate label column** (majority — `addMeasures.vue`, `scorePreferences.vue` ×7, `viewStaves.vue` ×2, `partInfo.vue` ×2 of 3, `timeSignature.vue` ×3, `textBlock.vue`): checkbox lives alone in one `col col-N` div, immediately followed by a sibling `col col-N` (or a `checkbox-input-label-div`) whose entire content is the descriptive label. → Full migration per FR-002/FR-003/FR-004: label text becomes the toggle's `label` prop, the label div is deleted, and the toggle's column width becomes the sum.
2. **Checkbox and label sharing one column** (`fontPicker.vue` ×2, `instrumentProperties.vue`, `newPart.vue` "Use Percussion Symbols"): the `<input>` and its `<label>` are both children of the *same* `col col-N` div (no second column to remove). → FR-001 still applies (swap to `toggle`, using the sibling label's text as the `label` prop), but there is no second column to delete or width to add — the toggle simply occupies the same single column, per FR-007's "no adjacent label div" carve-out (the label isn't in a *following div*, it's in the *same* div, so no column arithmetic applies).
3. **No adjacent label at all** (`staffGroups.vue` ×3, `partInfo.vue` "Include Next Stave" has a label but in the standard column-pair form so it's actually case 1 — the true case-3 example is `guitarTab.vue`'s and `newPart.vue`'s "2-Stave part" style rows which do have a label so they are case 1/2 too; the genuine case-3 examples are `staffGroups.vue`'s three per-row checkboxes, whose meaning is conveyed by column headers ("Group", "Start", "End" style headers) above the grid, not a per-row label div): → FR-001 applies (swap to toggle), FR-002–FR-004 do not (no label div to relocate or remove), per the Edge Cases section of the spec. The toggle's `label` prop is left empty (or a short accessible name derived from context, e.g. the header text) since there is no per-row text to move.

**Alternatives considered**: Treating case 2 as out of scope (since the spec literally says "following" a *div*, and here the label is a sibling *element*, not a following *div*) was considered, but rejected — the label is still adjacent, descriptive text that belongs on the toggle, and leaving it as a separate `<label>` next to a `toggle.vue` (which already renders its own label span) would produce a visibly duplicated/misplaced label. The pragmatic reading of the user's intent (make the dialogs consistent, no stray label markup) extends the relocation to same-column labels too, just without a column-width change since there's only one column involved.

## Decision: Preserve all existing bindings verbatim during the swap

**Rationale**: Every checkbox already drives its setting through one of `v-model="obj.prop"`, `:checked="expr"` + `@change="handler(...)"`, or a plain `@change` callback with no `v-model`. `toggle.vue` exposes the same shape needed to replicate any of these: `:initialValue="obj.prop"` for the starting value and `:changeCb="(value) => { obj.prop = value }"` (or the existing named handler, adapted to take the boolean value directly) for updates, plus `:disabled="expr"` for conditional disablement (e.g. `timeSignature.vue`'s `!supportsSymbol`, `measureFormat.vue`'s pattern for `pageBreak`/`padLeft`). This is a one-to-one substitution per instance; no shared helper/wrapper component is needed because `toggle.vue` already generalizes the pattern.

**Alternatives considered**: Introducing an intermediate wrapper component to reduce per-file boilerplate (e.g. a `checkboxRow` wrapper around `toggle.vue`) was considered, but rejected as unnecessary abstraction — `measureFormat.vue` shows `toggle.vue` is already ergonomic to call directly, and 26 direct call sites is not enough repetition to justify a new abstraction layer per the project's simplicity preference.
