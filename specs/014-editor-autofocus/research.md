# Phase 0 Research: Text Editor Autofocus on Open

All unknowns below were resolved by reading the existing codebase (no external research was needed — TipTap's own documented `autofocus`/`onCreate` options are already available in the installed version, `@tiptap/core` 3.30). No `NEEDS CLARIFICATION` markers remain in the Technical Context.

## 1. `v-if`-gated editors already remount on every mode transition

- **Finding**: All three host dialogs gate their embedded editor behind a `v-if` (not `v-show`) on a mode condition: `chord.vue`'s `<template v-if="mode === 'editing'">`, `lyric.vue`'s equivalent, and `textBlock.vue`'s `<div v-if="mode === 'editing'">`. Vue's `v-if` destroys and recreates the child component (and everything inside its `setup()`, including the `useEditor()` call that constructs the underlying TipTap `Editor` instance) every time the condition flips from false to true — unlike `v-show`, which only toggles CSS visibility and would keep the same component/editor instance alive.
- **Decision**: Because of this, a single fix applied at editor-construction time (inside `useEditor({...})`'s own options) automatically fires every time the editor becomes visible — whether that's the dialog's first-ever render (User Story 1) or a later return to editing mode after visiting the dialog's other view (User Story 2). No new dialog-level state, watcher, or emit is needed in `chord.vue`, `lyric.vue`, or `textBlock.vue`.
- **Rationale**: This is the simplest mechanism that satisfies both user stories with one change per editor component, and requires touching none of the three host dialogs, keeping the change fully additive and low-risk (FR-005).
- **Alternatives considered**: A dialog-level `watch(mode, ...)` that calls into the mounted editor's exposed `focus()`-like method after `nextTick()` (the general Vue pattern used elsewhere in this codebase for e.g. `textBlock.vue`'s `watch(mode, ...) { ... draggerRef.value?.start(); }` for the `moving` mode) — rejected as unnecessary extra wiring in three additional files, when TipTap's own per-editor-instance lifecycle options already cover the exact same "moment the editor becomes usable" trigger point without any dialog-level involvement at all.

## 2. `autofocus: 'end'` for the two single-paragraph editors

- **Finding**: `lyricEditor.vue` and `chordEditor.vue` both always hold a single-paragraph TipTap document (a lyric or chord symbol is one line of text; `chordEditor.vue`'s `chordGlyph` nodes are atomic but still live inline within that one paragraph). TipTap's built-in `useEditor`/`Editor` option `autofocus: FocusPosition` (`'start' | 'end' | 'all' | number | boolean | null`) is designed for exactly this: `'end'` resolves to `Selection.atEnd(doc)` — a collapsed cursor at the end of the document — and is applied once, automatically, right after the editor's initial content is set.
- **Decision**: Add `autofocus: 'end'` to the `useEditor({...})` call in both `lyricEditor.vue` and `chordEditor.vue`. No other code changes needed in either file.
- **Rationale**: `'end'` is the most natural landing spot for resuming/continuing to type a lyric or chord symbol (existing content, if any, is preserved and the cursor lands after it, ready to continue typing) and directly satisfies FR-001/FR-002 and FR-004 (a collapsed cursor position is never a text selection/highlight).
- **Alternatives considered**: `autofocus: 'start'` — rejected, since landing before existing text is a less natural continuation point than the end for both a lyric and a chord symbol. `autofocus: true` (equivalent to `'start'` per TipTap's own `resolveFocusPosition`, confirmed by reading `node_modules/@tiptap/core/dist/index.js`) — same rejection. A manual `onCreate`-driven `editor.commands.focus()` call (as used for `textGroupEditor.vue`, §3) — rejected as unnecessary extra code for these two components, since `autofocus: 'end'` is the purpose-built, declarative option for exactly this single-paragraph case.

## 3. `onCreate`-driven `editor.commands.focus()` for the multi-block text-group editor

- **Finding**: `textGroupEditor.vue`'s document can contain multiple text blocks (`SmoTextGroup.textBlocks`), of which only the "active" one (`activeBlockId`) is rendered as an editable paragraph — every other block is rendered as a read-only `textBlockAtom` node (`textGroupToHtml`, `TextBlockAtomNode`). A blunt `autofocus: 'end'` would place the cursor at the end of the *entire document*, which is only correct when the active block happens to be the last one; when it isn't, `'end'` would land the cursor adjacent to a read-only atom node instead of inside the actual editable active block. The component already has a proven answer to this exact problem: `activateBlock()` (fired whenever the user switches which block is active, including via `addBlock`/`removeBlock`/`goPrevious`/`goNext`) calls `rebuildContent()` followed by a bare `editor.value?.commands.focus()` (no explicit position argument), with an existing code comment acknowledging this is "best-effort" — exact caret placement within the newly-active block isn't guaranteed, but it reliably lands keyboard focus in the editor so the user isn't forced into an extra click.
- **Decision**: Add an `onCreate: ({ editor }) => editor.commands.focus()` callback to `textGroupEditor.vue`'s `useEditor({...})` call. `onCreate` is TipTap's lifecycle hook that fires exactly once, right after the editor instance and its initial document are ready — the multi-block-document-safe equivalent of what `autofocus` does for the single-paragraph editors, and it reuses the exact same `editor.commands.focus()` primitive (with the same "best-effort, no explicit position" behavior) that `activateBlock()` already relies on for the same underlying problem.
- **Rationale**: This directly satisfies FR-003 using the same already-accepted best-effort standard the component already applies elsewhere (`activateBlock()`), rather than introducing a new, more precise-but-unproven position-resolution mechanism (e.g., computing the exact document offset of the active block) that no other part of this component currently needs or does.
- **Alternatives considered**: `autofocus: 'end'` — rejected per the finding above (wrong block when the active block isn't last). Computing the active block's precise start/end offset in the document and passing it as an explicit `autofocus` position or `focus()` argument — rejected as unnecessary new precision/complexity beyond what `activateBlock()`'s existing, already-shipped behavior provides for the identical class of problem; revisit only if a future spec specifically asks for exact-position guarantees.

## 4. No text selection as a side effect (FR-004)

- **Finding**: TipTap's `resolveFocusPosition` (`node_modules/@tiptap/core/dist/index.js`) only produces a range selection (`'all'`, selecting the whole document) when explicitly asked to; `'end'` and a bare/no-argument `focus()` call both resolve to a collapsed cursor position (`Selection.atEnd(doc)` or the document's existing selection, respectively), never a highlighted range.
- **Decision**: No extra guard is needed — simply not passing `'all'` (or an explicit range) to either `autofocus` or `commands.focus()` already guarantees FR-004/SC-003 by construction.
- **Rationale**: Confirmed directly from TipTap's own source rather than assumed.
