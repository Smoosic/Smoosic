# Phase 0 Research: Vue-Based Chord Change Dialog

All unknowns below were resolved by reading the existing codebase (no external research was needed — this is an internal migration reusing established in-repo patterns, plus one substantively new piece: translating between a TipTap document and the existing chord-text string format). No `NEEDS CLARIFICATION` markers remain in the Technical Context.

## 1. Creation-function pattern and `dialogElements` mapping

- **Decision**: `SuiChordChangeDialogVue` is a plain exported function `(parameters: SuiDialogParams) => void`, mirroring `SuiLyricDialogVue` (`src/ui/dialogs/lyricVue.ts`, `010-vue-lyric-dialog`) exactly: `replaceVueRoot(modalContainerId)`, capture the initial selection/selector, set up reactive dialog-scoped state, `InstallDialog({ root, app: chordComp, appParams, dialogParams: parameters, commitCb, cancelCb })`.
- Each entry in `SuiChordChangeDialog.dialogElements.elements` (`src/ui/dialogs/chordChange.ts`) maps to a Vue control:

  | `smoName` | Legacy control | New Vue control |
  |---|---|---|
  | `verse` (labeled "Ordinality") | `SuiDropdownComponent`, 3 options (values `0`,`1`,`2` → labels "1","2","3") | `select.vue`, same 3 options |
  | `translateY` | `SuiRockerComponent` | `numberInput.vue`, `precision: 0`, explicit `minValue`/`maxValue` (unbounded like `010` research.md §5) |
  | `chordEditor` | `SuiChordComponent` (extends `SuiNoteTextComponent`) | new `chordEditor.vue` (TipTap) plus dialog-level next/previous/delete controls and the mode-toggle controls |
  | `chordSymbol` (labeled "Chord Symbol", exposed as "Symbols") | `SuiDropdownComponent`, 4 options (`csymDiminished`/`csymHalfDiminished`/`csymDiagonalArrangementSlash`/`csymMajorSeventh`) | `select.vue`, same 4 options; selecting one inserts a glyph into `chordEditor.vue` at the current position (see §2–§4) instead of the legacy simulated-keydown hack (`chordEditorCtrl.evKey({ key: '@'+value+'@', ... })`) |
  | `textPosition` (labeled "Text Position") | `SuiDropdownComponent`, 3 options (Superscript/Subscript/Normal) | `select.vue`, same 3 options; selecting one sets the "current text type" applied to subsequently-inserted content (§5) |
  | `font` | `SuiFontComponent` | `fontPicker.vue`, family/size only (weight forced `'normal'`, matching `010` research.md §6) |
  | `adjustWidth` | `SuiToggleComponent` | `toggle.vue`, editing `score.setChordAdjustWidth(...)` (score-wide, like Font — see §7) |

- **Rationale**: Directly requested by the feature description ("similar to how we did for the lyric dialog"); every substitute component already exists except the chord-specific TipTap editor and its glyph/text-position insertion commands, which are this feature's real work.
- **Alternatives considered**: None for the 1:1 control mapping — it is fully specified by `dialogElements` and confirmed against each existing component's prop contract, exactly as `010` did for the lyric dialog.

## 2. The chord-text format is independent of any editor, and must be preserved byte-for-byte

- **Finding**: A chord symbol's persisted `SmoLyric.text` (parser `SmoLyric.parsers.chord`) is not plain text. It is tokenized by `SmoLyric._tokenizeChordString(str)` (`src/smo/data/noteModifiers.ts`) into: runs of alphanumeric characters (literal text), single `^` characters (toggle superscript), single `%` characters (toggle subscript), and `@` characters that bracket a glyph key (e.g. `@diminished@`, `@b@`). This exact format is parsed independently at real render time by `getVexChordBlocks(lyric)` (`src/render/vex/smoAdapter.ts`) — used by `vxNote.ts`'s `addChordChangeToNote` to build the actual on-score VexFlow `ChordSymbol` — with **no dependency on `SuiChordEditor`, `SuiChordSession`, or any other editor class**. `toVex.ts` (measure-preview rendering) uses the identical `getVexChordBlocks` call.
- **Decision**: The real score rendering is already correct and requires no changes. The only job of the new Vue dialog is to produce (on commit/preview) and consume (on load) the exact same `SmoLyric.text` string format that `_tokenizeChordString`/`getVexChordBlocks` already understand, so `vxNote.ts` renders identically whether the text came from the legacy dialog or the new one.
- **Rationale**: This is what makes FR-006 through FR-011 and FR-021 achievable without touching the rendering pipeline at all — directly satisfies the Constraints in `plan.md` (byte-identical `SmoLyric.text` output) and Principle #3/#4 (no new UI dependency introduced into the renderer).
- **Alternatives considered**: Introducing a new/parallel chord-text representation (e.g., storing structured JSON instead of the token string) — rejected; it would require changing `vxNote.ts`/`smoAdapter.ts`/serialization and risks breaking existing scores and the (untouched, working) real rendering pipeline, far exceeding this feature's scope.

## 3. Recognized shortcut characters and their glyph keys (must match legacy exactly)

- **Finding**: `SuiChordEditor.evKey()` (`src/render/sui/textEdit.ts`) recognizes a typed character as a glyph shortcut via `VF.ChordSymbol.glyphs[evdata.key[0]]` (VexFlow's own glyph-name table) and, when recognized, stores the **raw typed character itself** as the glyph key (`this._addGlyphAt(this.textPos, evdata.key[0])`), which `getText()` later serializes as `'@' + key + '@'`. Separately, `src/common/vex.ts`'s locally-defined `ChordSymbolGlyphs` map (already exported) has entries for exactly `b`, `#`, `+`, `-`, `(`, `)`, `/` (each aliased to a `csymXxx`/`accidentalXxx` VexFlow code used elsewhere for editor-time glyph *metrics*, not for the persisted key) — confirming these seven are the complete, intentional shortcut set named in the feature description.
- **Decision**: `chordEditor.vue`'s keyboard-shortcut extension recognizes exactly `b`, `#`, `+`, `-`, `(`, `)`, `/` (membership test against the keys of the already-imported `ChordSymbolGlyphs`, `src/common/vex.ts`, rather than reaching into `VF.ChordSymbol.glyphs` — self-contained and equally complete for this fixed set). On a match, it inserts a `chordGlyph` node (§4) with `glyphKey` equal to the typed character itself (`'b'`, `'#'`, `'+'`, `'-'`, `'('`, `')'`, `'/'`) — identical to what the legacy editor persists — instead of inserting the literal character as plain text.
- **Rationale**: Directly satisfies FR-006 through FR-009, and guarantees the persisted `@key@` token is byte-identical to what the legacy dialog would have produced for the same keystroke.
- **Alternatives considered**: Mapping shortcut characters to the `csymXxx` code names instead of the raw character — rejected; would change the persisted text format from what existing scores/legacy dialog produce, and is unnecessary since VexFlow's `ChordSymbol.addGlyph` already accepts the raw shortcut character as a valid glyph name (confirmed by `getVexChordBlocks`/`addChordGlyph` passing `block.glyph` straight through).

## 4. Representing a music glyph inside the TipTap document

- **Finding**: Per the feature description, mixing Bravura (music-font) glyph rendering inline with ordinary text inside TipTap is not required to look correct — only the note's actual chord symbol on the score (FR-022) needs to. A glyph is also inherently a single, non-decomposable unit — it doesn't make sense for a user to place a text cursor "inside" a diminished-symbol glyph and edit half of it.
- **Decision**: Represent each inserted glyph (from a shortcut character or the Symbols dropdown) as a small custom **atomic inline TipTap Node** (`chordGlyph`, `inline: true, group: 'inline', atom: true, selectable: true`, no editable content), with one attribute, `glyphKey: string` — the exact string to be wrapped in `@...@` on serialization. It renders as a small `<span>` showing a short, legible ASCII placeholder derived from `glyphKey` (identity for the single-character shortcuts — `b`, `#`, `+`, `-`, `(`, `)`, `/` display as themselves; `diminished`/`halfDiminished`/`majorSeventh` display as short labels, e.g. `dim`/`hdim`/`maj7`, matching the Symbols dropdown's own option labels) — cosmetic only, per FR-022. Backspace/Delete removes the whole node as one unit (the standard behavior of an atomic ProseMirror node); it cannot be partially edited.
- **Rationale**: An atomic node (rather than, say, a Mark applied to one or more plain-text characters) guarantees the glyph is always treated, selected, and deleted as a single unit, which in turn guarantees the round-trip serialization in §6 always emits exactly one `@glyphKey@` token per glyph the user inserted — a plain-text-with-mark approach risks the user splitting a multi-character marked run (e.g. deleting one letter out of a "dim" placeholder) into two separately-marked runs, which would incorrectly serialize as two glyph tokens.
- **Alternatives considered**: A Mark-based approach (marking one or more literal characters as "this is glyph X") — rejected for the splitting risk above. Rendering the true Bravura codepoint character directly (as literal PUA/SMuFL text using a `font-family: Bravura` inline style) instead of an ASCII placeholder — not rejected outright (it may render acceptably in most browsers, since mixing an inline `<span style="font-family:...">` inside a contenteditable region is ordinary CSS, not a TipTap limitation), but deliberately not required by this plan: the feature description explicitly permits a non-faithful in-editor look, so the simpler ASCII placeholder is the baseline; using the real glyph character as the placeholder's display text (still inside the same atomic node/attribute structure) is a low-risk, purely cosmetic enhancement that can be decided at implementation time without changing this design.

## 5. Text Position (superscript/subscript) — use the stock TipTap marks

- **Finding**: `@tiptap/extension-superscript` and `@tiptap/extension-subscript` are already listed in `package.json` but are not imported anywhere in `src/` today — unlike the glyph-mixing problem in §4, ordinary vertical text positioning (smaller, raised/lowered text) is a standard rich-text feature with no music-font dependency, so these stock marks render *accurately* in `chordEditor.vue`, not just as a placeholder.
- **Decision**: Use `Superscript`/`Subscript` from these packages as ordinary TipTap marks. The Text Position dropdown does not directly write `^`/`%` characters; it sets a `currentTextType: Ref<0|1|2>` (`normal`/`superscript`/`subscript`, matching `SuiInlineText.textTypes`) that determines which mark (if any) is applied to whatever is inserted *next* — plain text typed going forward, or a `chordGlyph` node inserted via a shortcut/dropdown — mirroring the legacy `SuiChordEditor.textType` field (`_addGlyphAt`/`parseBlocks` both stamp `this.textType` onto each new block) exactly. Selecting Normal calls `unsetSuperscript().unsetSubscript()` (via `chain()`) going forward; selecting Superscript/Subscript unsets the other and sets the requested one. Previously-typed/inserted content is untouched (FR-011, second half).
- **Rationale**: Directly satisfies FR-011, and — as a byproduct of using real marks — gives the user a materially *more* accurate in-editor preview for text positioning than the legacy dialog's own SVG editor might have while typing, at no extra implementation cost (the extensions are already a dependency).
- **Alternatives considered**: A custom mark mirroring the `chordGlyph` node's placeholder approach (no real vertical offset shown) — rejected as strictly worse with no benefit, given the stock marks are already available and involve no music-font rendering concerns.

## 6. Serializing the TipTap document back to the `SmoLyric.text` chord format

- **Decision**: A new, pure, framework-adjacent module, `src/ui/components/dialogs/chordText.ts`, holds the encode/decode logic, isolated from ProseMirror specifics as much as practical:
  - **`type ChordSegment = { kind: 'text', text: string, textType: 0|1|2 } | { kind: 'glyph', glyphKey: string, textType: 0|1|2 }`** — a simple, neutral intermediate form.
  - **`decodeChordText(raw: string): ChordSegment[]`** — tokenizes `raw` via `SmoLyric._tokenizeChordString(raw)` (reused verbatim, `src/smo/data/noteModifiers.ts`), tracking a running `textType` that starts at `SuiInlineText.textTypes.normal` and updates via `SuiInlineText.getTextTypeResult(textType, SuiTextEditor.textTypeFromChar(token))` whenever the token is `^`/`%` (mirroring `SuiChordEditor._setSymbolModifier` exactly); text runs and `@glyphKey@` runs are emitted as `ChordSegment`s stamped with the `textType` active at that point.
  - **`encodeChordText(segments: ChordSegment[]): string`** — walks `segments` in order, tracking `previousType` starting at `normal`; whenever a segment's `textType` differs from `previousType`, emits `SuiTextEditor.textTypeToChar(SuiInlineText.getTextTypeTransition(previousType, segment.textType))` first and updates `previousType`; then emits either the segment's literal text (`kind: 'text'`) or `'@' + glyphKey + '@'` (`kind: 'glyph'`).
  - `chordEditor.vue` owns the one remaining, ProseMirror-specific mapping: `ChordSegment[] ⇄ TipTap JSON document` (a `text` segment becomes a text node with the `Superscript`/`Subscript` mark applied per its `textType`; a `glyph` segment becomes one `chordGlyph` node, similarly marked).
- **Rationale**: Reusing `SmoLyric._tokenizeChordString` and `SuiInlineText`/`SuiTextEditor`'s existing static toggle-transition tables (rather than re-deriving the `^`/`%` state machine) guarantees the new encode/decode logic agrees with the legacy editor and with `getVexChordBlocks` on every edge case (nested/doubled toggles, transitioning directly from superscript to subscript, etc.) without duplicating or re-verifying that logic. Isolating `ChordSegment[]` as a neutral intermediate form keeps the pure round-trip logic (the part most worth double-checking) independent of ProseMirror's document shape, and testable standalone if the tasks phase adds a unit test for it.
- **Alternatives considered**: Re-deriving the toggle/transition logic directly against ProseMirror mark state (e.g., comparing `Superscript`/`Subscript` presence node-to-node and hand-rolling the `^`/`%` emission rules) without going through `ChordSegment[]`/the shared statics — rejected; it would duplicate logic that already exists and is exercised by the legacy dialog and the real rendering pipeline, with real risk of subtly disagreeing with `getTextTypeTransition`'s truth table on a corner case (e.g. superscript→subscript in one step).

## 7. Font and Adjust Note Width are score-wide (not per-note), matching Font's precedent in `010`

- **Finding**: `SuiChordChangeDialog.changed()` (`src/ui/dialogs/chordChange.ts`) commits Font via `this.view.setChordFont(fontInfo)` (`SuiScoreViewOperations.setChordFont` → `score.setChordFont(fontInfo)`, cascading to every staff) and Adjust Note Width via `this.view.score.setChordAdjustWidth(value)` (`SmoScore.setChordAdjustWidth`, `src/smo/data/score.ts:1372`, likewise cascading `staff.setChordAdjustWidth(...)` to every staff) — both score-wide settings, seeded for display from the current note's chord symbol (`lyric.fontInfo`, `lyric.adjustNoteWidthChord`) but not written back to that single lyric.
- **Decision**: Preserve this exactly, mirroring `010` research.md §6's treatment of the Lyric dialog's Font control. `chord.vue`'s Font control is seeded from the current note's chord symbol but commits via `view.setChordFont({ family, size, weight: 'normal' })`; its Adjust Note Width toggle is seeded from `lyric.adjustNoteWidthChord` but commits via `view.score.setChordAdjustWidth(value)` directly (matching the legacy dialog's direct `view.score.*` call, bypassing `SuiScoreViewOperations` — there is no wrapped equivalent for this one setting today, and this plan does not add one).
- **Rationale**: FR-012/FR-013/FR-020 ask for parity with legacy `SuiFontComponent`/toggle behavior; changing either to a true per-note setting would be a scope-expanding behavior change beyond what the spec or feature description requested.
- **Alternatives considered**: Wrapping `score.setChordAdjustWidth` in a new `SuiScoreViewOperations` method for symmetry with `setChordFont`/`setLyricFont` — rejected as an unrequested API change; calling `view.score.setChordAdjustWidth(...)` directly from `chord.vue` (as the legacy dialog does from `chordChange.ts`) is a faithful, minimal port.

## 8. Navigation, delete, mode state machine, no Remove control, OK/Cancel parity, auto-start-editing

- **Finding**: `SuiChordComponent` (`src/ui/dialogs/components/noteText.ts`) extends the same `SuiNoteTextComponent` base as `SuiLyricComponent`, and `SuiChordChangeDialog.bindElements()` removes the dialog's Remove button identically to `SuiLyricDialog` (`$(dgDom.element).find('.remove-button').remove()`), unconditionally starts an edit session on display (`this.chordEditorCtrl.startEditSession()`), and wires both OK and Cancel to the same `_complete()` with no `groupUndo`/`undo()` — the exact same shape `010` already researched and ported for the lyric dialog (research.md §3–§4, §7–§9).
- **Decision**: Port `010`'s decisions for these mechanics verbatim onto the chord dialog: bypass `SuiChordSession`/`SuiChordEditor`'s SVG editor entirely, reimplementing `navigate`/`deleteCurrent`/`loadNote` directly against `SmoSelection.nextNoteSelectionFromSelector`/`lastNoteSelectionFromSelector` and `view.addOrUpdateLyric`/`view.removeLyric` (which already work generically for any `SmoLyric`, keyed on `verse`+`parser` — confirmed in `src/render/sui/scoreViewOperations.ts`, no chord-specific branching needed); a single `mode: Ref<'editing'|'dialog'>`; no `removeCb`; identical `commitCb`/`cancelCb` behavior; `mode` initialized to `'editing'` unconditionally on every dialog open, loading the initially-selected note's chord symbol for ordinality `0`.
- **Rationale**: This is the same category of dialog as the lyric dialog (`SuiNoteTextComponent`-derived, session/editor-per-note architecture) with the same legacy mechanics; there is no reason to make a different design choice here than `010` already made and validated.
- **Alternatives considered**: None beyond what `010`'s research.md already considered and rejected for the equivalent lyric-dialog mechanics.

## 9. Live preview and position marker

- **Finding**: `012-lyric-live-preview-cursor` already added a debounced (`PREVIEW_DEBOUNCE_MS = 400`) `preview` emit to `lyricEditor.vue` (`onUpdate: schedulePreview`) and a subtle position-marker mechanism in `lyric.vue` (`SvgHelpers.renderLyricPositionMarker`), reusing `commitIfChanged()` unchanged as the one write both navigation and the periodic preview share.
- **Decision**: Reuse the identical pattern in `chordEditor.vue`/`chord.vue`: `onUpdate: schedulePreview` (same 400ms debounce) emits `preview`; `chord.vue`'s `onEditorPreview` calls the chord-dialog's own `commitIfChanged()` (which reads the current TipTap doc, runs it through `encodeChordText`, and — if the resulting string differs from what was loaded — calls `view.addOrUpdateLyric`), satisfying FR-021 (periodic, debounced, non-interrupting score update) using the exact mechanism already validated for lyrics. The position marker itself (FR — none explicitly required by this spec, unlike `012`'s lyric-specific spec) is out of scope here: `013-vue-chord-dialog`'s spec does not ask for a position-marker cursor, only for the periodic score update; this plan does not add one for chords.
- **Rationale**: Directly satisfies FR-021/FR-022 using an already-proven pattern; avoids scope creep by not porting `012`'s marker feature, which was never requested for chords.
- **Alternatives considered**: Porting the `012` position marker to chords as well for consistency — rejected as out of scope; nothing in the `013` feature description or spec asks for it, and adding it would be an unrequested scope expansion.

## 10. `^`/`%` keyboard shortcuts for Text Position (added post-implementation)

- **Finding**: Per an explicit follow-up correction from the feature owner, typing `^` while the chord text editor is active must toggle the typing text-position toward **Subscript** (not Superscript), and typing `%` must toggle it toward **Superscript** (not Subscript) - the inverse of what the internal persisted-format's own toggle characters mean (`SuiTextEditor.textTypeToChar`: superscript ⇒ `'^'`, subscript ⇒ `'%'`, per §6 above). Both use the same three-way toggle rule already established for the Text Position dropdown (§5, FR-011): from Normal → the named mode; from that same mode → back to Normal; from the *other* mode → switch directly to the named mode.
- **Decision**: This is a UI/keyboard-shortcut convenience binding, entirely independent of the persisted-text-format's internal `^`/`%` convention - which character a user presses to *reach* a given typing text-position has no bearing on which character `encodeChordText` later *emits* to represent that state in the persisted string (that emission is driven solely by `SuiInlineText.getTextTypeTransition`/`SuiTextEditor.textTypeToChar` comparing consecutive segments' `textType`, never by input history). So no conflict exists with §6's codec: implement `^`/`%` as two additional entries in `chordEditor.vue`'s keyboard-shortcut extension, each computing `SuiInlineText.getTextTypeResult(currentTypingTextType, targetType)` with a **locally-defined** `char → targetType` mapping (`'^' → subScript`, `'%' → superScript`) that is deliberately the reverse of `SuiTextEditor.textTypeFromChar`'s mapping (which is not reused here), then emitting the result up to `chord.vue` (a new `textTypeChange` emit) to update `currentTextType` - the same ref the Text Position dropdown already writes to, so either input method leaves the other in a consistent, reflected state (the dropdown's `:key="currentTextType"` binding already re-renders it to match).
- **Rationale**: Implements the feature owner's explicit, twice-stated correction exactly as given; reusing `getTextTypeResult` (generic in its two numeric arguments) for the toggle arithmetic avoids re-deriving the three-way toggle rule a second time, while the char→target mapping itself is intentionally new/local rather than reusing `textTypeFromChar`, since that function's mapping is fixed to the persisted-format's own (different) convention.
- **Alternatives considered**: Reusing `SuiTextEditor.textTypeFromChar` directly (which would give `^`→superscript, `%`→subscript) - rejected; it does not match the explicitly-requested behavior for this new editor-only keyboard shortcut, even though it is the convention used elsewhere in this same codebase for the persisted-format's toggle characters.
