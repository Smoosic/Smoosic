# Phase 0 Research: Landmark Text Menu

## 1. `SmoTextGroup.purpose` is a dormant field today — it must be wired into construction/serialization for this feature to work at all

**Finding**: `SmoTextGroup.purposes` (`src/smo/data/scoreText.ts:406-411`) and the `purpose: number` class field (`scoreText.ts:501`) already exist, and `createTextForLayout` (`scoreText.ts:458-482`, used today by `xmlToSmo.ts:136-148` to create Title/Subtitle/Composer text on MusicXML import) already does `params.purpose = purpose;` before constructing. But `purpose` is **not** in `SmoTextGroup.attributes`, `nonTextAttributes`, or `simpleAttributes` (`scoreText.ts:412-423`), and the constructor only copies fields listed in `nonTextAttributes` (`scoreText.ts:618-619`). A grep of the whole `src/` tree for `.purpose` shows zero call sites anywhere that read `SmoTextGroup`'s `purpose` back (the other `.purpose` hits are an unrelated `SuiInlineText.purpose` string field and unrelated `SmoScore.fontPurposes` lookups). So today, every `SmoTextGroup` — including ones created via `createTextForLayout` — silently ends up with `purpose === NONE` after construction, and `serialize()`/`deserialize()` never persist a purpose either.

**Decision**: Add `'purpose'` to `SmoTextGroup.nonTextAttributes` (and therefore `attributes`). This makes the constructor actually copy it from `params`, and makes `serialize()` (via `serializedMergeNonDefault`) emit it whenever it's not `NONE`.

**Rationale**: This feature's core FR-006 ("reopening an existing landmark opens its dialog instead of duplicating it") and FR-013/FR-014 (disabling free-text editing and pagination-type change specifically for landmarks) both require a real, persisted way to ask "is this text group a landmark, and which one?" `purpose` is already exactly that concept, already named in the spec's own vocabulary, and adding it to the attribute list is a one-line, additive change. Constitution Principle #1 (serialization): a legacy score's JSON has no `purpose` field on any text group, so `smoSerialize.serializedMerge`'s existing default-filling (already how every other field in the list is defaulted) fills in `NONE` — identical to today's behavior. A plain "Score Text" created via the existing `textBlockDialogMenuOption` also defaults to `NONE` and round-trips with zero diff in saved JSON (since `serializedMergeNonDefault` only emits non-default values).

**Alternatives considered**: A separate boolean (`isLandmark`) instead of reusing `purpose` — rejected as redundant; `purpose !== NONE` already answers "is this a landmark" precisely, and reusing it also answers "which one," which a boolean wouldn't.

## 2. Landmark placement/font defaults: a new table, not a mutation of `purposeToFont`

**Finding**: `SmoTextGroup.purposeToFont` (`scoreText.ts:427-454`) already has TITLE/SUBTITLE/COMPOSER/COPYRIGHT entries, but its font sizes (18/16/12/12) don't match this feature's required defaults (Title 24px, Subtitle 18px), and it has no PAGE/PART/DATE entries. It is actively used, unmodified, by `xmlToSmo.ts`'s MusicXML-import Title/Subtitle/Composer creation (research §1) — changing its values would silently change import-time sizing/positioning, an unrelated regression risk outside this feature's scope.

**Decision**: Add a new static map `SmoTextGroup.landmarkPlacements: Record<number, SmoTextPlacement>` covering all seven landmark purposes with this feature's own defaults, and a new static method `SmoTextGroup.createLandmarkText(purpose: number, text: string, layout: ScaledPageLayout): SmoTextGroup`, based on `createTextForLayout`'s x/y/width arithmetic (`scoreText.ts:458-482`) but reading `landmarkPlacements` instead of `purposeToFont`, and additionally setting `pagination: SmoTextGroup.paginations.EVERY` (research §4) on the constructed group. `createTextForLayout` itself is left untouched.

**Two placement bugs found and fixed after the first implementation pass** (both were in code copied verbatim from `createTextForLayout`, so `createTextForLayout`/the MusicXML-import path likely carries the same two bugs, left unfixed there per this decision's own "leave it untouched" rationale):

1. **Horizontal center-x was page-width-relative, not margin-relative.** The original arithmetic computed the target x as `pageWidth * xPlacement`, ignoring `leftMargin`/`rightMargin` entirely. For `xPlacement === 0.5` that lands on the exact horizontal center of the raw page, not the center of the printable area between the margins — visibly wrong whenever margins aren't equal, and conceptually wrong even when they are (a page-layout feature should measure "centered" relative to its margins, not the paper edge). **Fix**: `centerX = leftMargin + (pageWidth - leftMargin - rightMargin) * xPlacement`, i.e. `xPlacement` is now a fraction of the printable width, measured from the left margin.
2. **The width-based centering shift was computed but never applied.** The original code did `x -= width / 2` on the *local* `x` variable, but `st` (the `SmoScoreText` whose `.x` field is what actually gets rendered) had already been constructed with the un-shifted `x` moments earlier — the decremented local variable was simply discarded, so every landmark's text rendered with its *left edge* at the target center point instead of being centered on it (visually: text appears to start at the horizontal center and run to the right, "too far right", exactly as reported after using the feature). **Fix**: construct `st` first, call `st.estimateWidth()`, then explicitly assign `st.x = centerX - (width / 2)` — no local variable is left unapplied.

Placement table (positions expressed the same way the existing `purposeToFont` entries already do — `xPlacement` is a fraction of the *printable width between the margins* (0.5 = centered between the margins) from the left margin; `yOffset` > 0 is pixels down from the true top of the page, `yOffset` < 0 is pixels up from the true bottom of the page — **not** the top/bottom margins, corrected in §2b below per FR-018):

| Purpose | xPlacement | yOffset | fontSize | Rationale |
|---|---|---|---|---|
| TITLE | 0.5 | +24 | 24 | Spec FR-007: centered, top of page, "1em below the top margin" — yOffset equals this entry's own fontSize (1em). |
| SUBTITLE | 0.5 | +52 | 18 | Spec FR-008: centered, below Title's position — preserves the original 28px baseline-to-baseline gap now that Title moved from yOffset 4 to 24 (4→24 is a +20 shift; 32+20=52). |
| COMPOSER | 0.8 | +10 | 12 | Spec FR-011: upper right; matches existing `purposeToFont` COMPOSER corner (0.8, near top) — size follows the "existing default text styling" assumption since only Title/Subtitle sizes were specified. |
| COPYRIGHT | 0.5 | -12 | 12 | Spec FR-009: centered, bottom; matches existing `purposeToFont` COPYRIGHT entry. |
| DATE | 0.5 | -28 | 12 | Spec FR-009: centered, bottom — offset from Copyright's row so the two don't start out stacked exactly on top of each other. |
| PAGE | 0.8 | +24 | 12 | Spec FR-010: upper right — offset from Composer's row for the same reason. |
| PART | 0.8 | +38 | 12 | Spec FR-011: upper right — offset from Composer/Page rows for the same reason. |

**Rationale**: Keeps the MusicXML-import path (research §1's `createTextForLayout` call sites) completely unaffected while giving this feature its own explicit, spec-matching defaults. Per spec Edge Cases, upper-right/bottom-center items are allowed to visually overlap at creation since the user already has font/position controls (FR-015/FR-016) to separate them; the small offsets above are a reasonable starting layout, not a load-bearing requirement. `yOffset` is treated as baseline-relative to the true page edge (matching how the rendering pipeline uses `SmoScoreText.y`, `textRender.ts`'s `getLogicalBox`; see §2b for the correction from margin-relative to page-edge-relative) — "1em from the page edge" is implemented as an additive pixel offset equal to the font's own size in this same idiom, not a from-scratch ascent/descent calculation, since the latter isn't observable without a running browser in this environment; further fine-tuning after a visual check (`quickstart.md`) may still be warranted.

**Alternatives considered**: Editing `purposeToFont` in place and adding the three missing entries there — rejected because its Title/Subtitle sizes are consumed by the unrelated MusicXML-import feature and must not change.

## 2b. Vertical anchor corrected from margin-relative to page-edge-relative (spec Clarifications, 2026-09-24, FR-018/SC-007)

> **Superseded for top-anchored purposes by §2c below** (same day, follow-up refinement, FR-019/FR-020): the flat "one em" buffer this section establishes was replaced by a margin-proportional base position plus stacking. This section's bottom-anchored (Copyright/Date) conclusion is unaffected and still applies as written.

**Finding**: §2's original `y` formula anchored top-of-page landmarks to `topMargin` and bottom-of-page landmarks to `bottomMargin`: `y = yOffset > 0 ? topMargin + yOffset : pageHeight + yOffset - bottomMargin`. This was flagged as incorrect by the user after visual testing: `topMargin`/`bottomMargin` bound the region the score's music systems render into (per Constitution context: "This is an SVG application... Smoosic rendering is done using the vexflow library" — margins are a music-layout concept, not a text-layout one), so a landmark positioned a small offset *inside* the margin (as §2's original TITLE/SUBTITLE/COMPOSER/PAGE/PART/COPYRIGHT/DATE values all were) lands in the same vertical band the first/last music system occupies, and can visually collide with it. The spec's Clarifications session confirmed the fix: anchor to the physical page edge instead, with a small buffer (FR-018: "one em of that landmark's own font size").

**Decision**: In `createLandmarkText`, drop `topMargin`/`bottomMargin` from the `y` formula entirely: `y = yOffset > 0 ? yOffset : pageHeight + yOffset` — top-anchored purposes measure `yOffset` pixels down from the true page top (`y = 0`); bottom-anchored purposes measure `|yOffset|` pixels up from the true page bottom (`y = pageHeight`). `topMargin`/`bottomMargin` are no longer read by this method at all (`leftMargin`/`rightMargin` are still used for horizontal centering, per §2 — this correction is vertical-only, matching the spec Clarifications' explicit scope: "ignore the top and bottom margins," left/right unaffected). The existing `landmarkPlacements` table's `yOffset` magnitudes (research §2's table) are **kept unchanged** — TITLE's `24` already equals its own 24px `fontSize` (an exact "1em" buffer, satisfying FR-018 precisely), and the other purposes' smaller magnitudes (10, -12, -28, 24, 38, and SUBTITLE's 52) were already small, page-edge-appropriate buffer/stacking values; only the *reference point* they're measured from changes, not their numeric values.

**Rationale**: This is the minimal, directly-traceable fix for the reported bug and the clarified requirement — a one-line arithmetic change (delete two terms) rather than a redesign of the placement table. Recalculating every purpose's `yOffset` to be an exact multiple of its own font size was considered but rejected as unnecessary: FR-018 only requires "a small buffer... one em," not an exact-to-the-pixel formula for every purpose, and the existing values are already small and were already tuned to look reasonable relative to each other (e.g. SUBTITLE sitting visibly below TITLE); re-deriving them from scratch would be speculative precision with no corresponding spec requirement, and would risk introducing a new, unreviewed visual regression in exchange for no testable benefit.

**Alternatives considered**: Keeping the margin terms but subtracting them back out with a compensating constant (e.g. `topMargin + yOffset - topMargin`) — rejected as needlessly obfuscated; the correct fix is to not read `topMargin`/`bottomMargin` in this calculation at all, which also makes the "must never render inside the margin" invariant (FR-018) visible by inspection: the variables simply aren't in scope for the vertical calculation anymore.

## 2c. Top-anchored base position made margin-proportional, plus stacking for landmarks sharing a column (FR-019/FR-020)

**Finding**: §2b's flat "one em" buffer for top-anchored purposes was a reasonable interim answer, but the user asked for something more precise once they could see it: the base position (when nothing else is above a landmark) should scale with the actual top margin rather than being a fixed small constant, and landmarks that stack in the same horizontal column (Subtitle under Title; Page number/Part under Composer) should be positioned relative to *each other*, not each independently computed from the page edge.

**Decision**:
- **Base case** (nothing above): a top-anchored landmark's visual top starts at `Math.max(0, topMargin / 2 - height)`, where `height` is that specific text's own estimated rendered height (`SmoScoreText.estimateHeight()`, new method, mirroring the existing `estimateWidth()` — both build a `TextFormatter` from the block's font info and read real glyph metrics; `estimateHeight()` calls `TextFormatter.getYForStringInPx(text).height` rather than summing per-character widths). This keeps the landmark within the *top half* of the margin (leaving the bottom half of the margin, closest to the music, clear) for ordinary cases, and never lets it start above the page's true top edge even for a landmark taller than half the margin.
- **Stacked case** (something already above, in the same column): the new landmark's visual top is set flush to the existing one's visual bottom (`above.logicalBox.y + above.logicalBox.height`), read from the *already-rendered* geometry of the existing landmark (populated by the normal render pass the moment it was added to the score — `scoreRender.ts`'s `renderTextGroup`), not recomputed/estimated.
- **Columns**: two fixed top-anchored columns, defined once in `src/ui/menus/text.ts` (`LANDMARK_COLUMNS`): `[TITLE, SUBTITLE]` and `[COMPOSER, PAGE, PART]`. A new helper, `findAboveLandmark(purpose, view)`, walks backward from a purpose's index in its column and returns the nearest already-existing landmark, or `undefined` if none of the preceding purposes in that column exist yet (in which case the base case applies). This lookup lives in the menu layer (which already has `findLandmark`/score access), not in `scoreText.ts`, keeping `SmoTextGroup.createLandmarkText`'s signature simple: it takes the resolved `above?: SmoTextGroup | null` as a plain parameter rather than knowing about columns itself.
- **`st.y`'s baseline-like semantics**: per `textRender.ts`'s `_calculateBoundingClientRect`/`getLogicalBox` (`nbox.y = nbox.y - nbox.height`), the renderer treats a text block's raw `y`/`startY` as a bottom/baseline-like coordinate, deriving the visual top as `y - height`. So to make a text's *visual top* equal some target `top`, the code must set `st.y = top + height`. This is applied for both the base case (`Math.max(topMargin/2, height)`, algebraically `max(0, topMargin/2 - height) + height`) and the stacked case (`(above.logicalBox.y + above.logicalBox.height) + height`).
- **Bottom-anchored purposes (Copyright, Date) are unchanged** — the user's refinement request explicitly named only the top-margin case and "subtext, composer, pages" (top-anchored purposes); Copyright/Date keep §2b's `y = pageHeight + yOffset` exactly as-is.
- **`landmarkPlacements`' top-anchored `yOffset` values became sign-only placeholders**: since the actual vertical position for TITLE/SUBTITLE/COMPOSER/PAGE/PART no longer reads `yOffset`'s magnitude at all (only its sign, to distinguish top- vs. bottom-anchored), those five entries' `yOffset` was changed to a canonical `1` (was: 24/52/10/24/38, magnitudes that would now be misleading dead weight) with a doc comment explaining the sign-only convention. Bottom-anchored entries (Copyright `-12`, Date `-28`) are untouched since their magnitude is still load-bearing.

**Rationale**: Deriving the base position from the *actual* top margin (rather than a fixed constant) makes the buffer meaningfully adapt if a score's margin changes, directly satisfying the refined ask; using real rendered geometry (`logicalBox`) for the stacked case is more accurate than trying to re-estimate an existing landmark's height a second time, and is already-available data (every added text group gets rendered immediately via `addTextGroup`'s `rerenderTextGroups()`). Fixed columns (rather than, say, a fully general "stack everything below everything else in creation order") keep the behavior predictable and match the two visually distinct clusters the spec already describes (top-center: Title/Subtitle; upper-right: Composer/Page number/Part) — see spec.md's new Edge Case entry for what happens when a column is populated out of order.

**Alternatives considered**: Passing `above` as a purpose number and having `createLandmarkText` look it up itself — rejected; `SmoTextGroup` (the `src/smo/data` layer) has no reference to the score's other text groups or to `SuiScoreViewOperations`, and reaching for one would be a layering violation (Constitution Principle #4). Keeping `createLandmarkText`'s only additional parameter as an already-resolved `SmoTextGroup | null` keeps the data layer free of any lookup/traversal responsibility. Also considered: adding a small explicit gap between stacked landmarks (e.g. a few px below the "flush" position) — rejected as unrequested; "offset by whatever is above them" was taken literally (flush stacking), matching the precision the user asked for elsewhere in this same request (an exact margin-based formula, not an approximate one).

## 2d. Upper-right landmarks changed from center-justified-at-a-point to right-justified-against-the-margin (FR-021)

**Finding**: §2's original horizontal formula treated every purpose uniformly as "centered around a point `xPlacement` fraction of the way across the printable width" — for the upper-right cluster (Composer, Page number, Part) that point was `xPlacement = 0.8`, an arbitrary approximation of "near the right side," with the text's *center* (not its right edge) landing there. The user clarified the actual intent: these three should be truly right-justified, with the text's right edge flush against the right margin, matching how "right-justified" text is conventionally defined (right edge at the alignment boundary), not centered near it.

**Decision**: Introduced a new `SmoLandmarkPlacement` interface (`fontFamily`, `fontSize`, `xJustify: 'center' | 'right'`, `xPlacement?` — required only when `xJustify === 'center'`, `yOffset`), used solely by `landmarkPlacements` (kept distinct from the shared `SmoTextPlacement`, which `purposeToFont`/`createTextForLayout` still use unmodified). `createLandmarkText` now branches on `xJustify`:
- `'center'` (Title, Subtitle, Copyright, Date): unchanged from §2 — `centerX = leftMargin + printableWidth * xPlacement`, then `st.x = centerX - width/2`.
- `'right'` (Composer, Page number, Part): `st.x = (pageWidth - rightMargin) - width` — the text's right edge (`st.x + width`) lands exactly at `pageWidth - rightMargin` (the right margin line), with no `xPlacement` needed at all.

**Rationale**: This is a direct, literal implementation of the clarified rule ("right margin minus length of the text"), and removes the arbitrary `0.8` approximation entirely rather than trying to tune it further — right-justification is an exact geometric relationship (edge-to-edge), not a point estimate, so a dedicated formula is more correct than continuing to approximate it via the centering formula with a magic constant.

**Alternatives considered**: Keeping a single `SmoTextPlacement`-shaped table and encoding "right justify" as, e.g., `xPlacement: 1.0` with a special-cased meaning — rejected as implicit and easy to misread; a named `xJustify` field states the two distinct layout behaviors explicitly rather than overloading `xPlacement`'s existing "fraction of printable width" meaning with a second, incompatible interpretation.

## 2e. Page number's right edge didn't match Composer's — width was estimated from the marker template, not the rendered text (found via user feedback after §2d)

**Finding**: §2d's `'right'` formula (`st.x = (pageWidth - rightMargin) - width`) always produces the same right edge (`pageWidth - rightMargin`) *algebraically*, regardless of `width` — so Composer and Page number's ending X should have been identical. But Page number's `text` (from `resolveLandmarkText`) is the **literal, unsubstituted marker template** `'Page ### of @@@'` (18 characters, including two 3-character marker sequences) — the *real* rendered text, after `SmoTextGroup.getPagedTextGroups`'s per-page `.replace('###', ...)`/`.replace('@@@', ...)` (research §4), is much shorter (e.g. `'Page 1 of 3'`, 11 characters) for any realistically-sized score. `createLandmarkText` estimates width from the literal stored `text` (the only text it has at creation time), so Page number's computed `width` is a significant **over-estimate** of what actually renders. Since `st.x = target - width`, an over-estimated `width` pushes `st.x` too far left, and the real rendered right edge (`st.x + realWidth`) then falls **short of** (to the left of) the target margin by exactly `(estimatedWidth - realWidth)` — while Composer (whose stored and rendered text are identical, no markers) hits the target exactly. The user observed this as "composer is always to the right of page" (Composer's right edge sits at the true margin; Page number's falls short of it, appearing further left).

**Decision**: Added an optional 5th parameter to `createLandmarkText`, `measureText?: string`, used **only** to compute `width`/`height` (via a temporary swap: `st.text = measureText` before `estimate*()`, then restored to `st.text = text` before continuing) — the group's actually-stored, actually-substituted-per-page `text` is untouched. A new caller-side helper, `resolveLandmarkMeasureText(purpose, view, resolvedText)` in `src/ui/menus/text.ts`, returns a representative already-substituted string for Page number (`` `Page 1 of ${pageLayouts.length}` ``) and just passes `resolvedText` through unchanged for every other purpose (none of which have markers).

**Rationale**: This is a narrowly-scoped fix for the one purpose that actually has this template/rendered-text mismatch (Page number is the only `resolveLandmarkText` branch that returns marker syntax); every other purpose's `measureText` call is a no-op (`measureText === text`). A full architectural fix — persisting `xJustify`/margin info on `SmoTextGroup` so `getPagedTextGroups` could re-right-justify each page's *actual* substituted text independently — was considered and rejected as disproportionate: it would need new persisted fields (Constitution Principle #1 migration surface) to fix a single purpose, and even then would only be exactly right on pages whose digit-count happens to match the representative estimate (e.g. a 9-page score's page 9 render as "9", not "1", a 1-character difference) — the representative-string approach already gets this right for the overwhelmingly common case (page/total-page numbers in the same digit-count range as the estimate) at a fraction of the complexity, which is an acceptable trade-off since exact per-page right-justification down to the pixel wasn't the ask — matching Composer's edge was.

**Alternatives considered**: Estimating width from the *widest possible* substitution (e.g. always assuming 3-digit numbers, matching the marker's own literal length) — rejected as it would systematically leave Page number's usual (1-2 digit) rendering short of the margin by design, the same visible symptom as today, just smaller; a representative "typical" substitution (current page 1, actual total page count) is a better central estimate for the common case.

## 2f. Column stacking (FR-020) was order-dependent — fixed to look at whichever column member already exists, not a fixed sequence (found via user feedback after §2c)

**Finding**: §2c's `findAboveLandmark` walked backward from a purpose's *fixed index* in `LANDMARK_COLUMNS` (`[COMPOSER, PAGE, PART]`) looking for an earlier-index purpose that already exists. Since `COMPOSER` was always index 0, it could **never** find anything "above" it — regardless of whether `PAGE` or `PART` already existed in the score. So creating Page number first, then Composer, left Composer computing the same FR-019 base position Page number had already used, landing exactly on top of it (identical Y) — the user's second reported bug ("if pages are placed before composer, they end \[up\] having the same Y").

**Decision**: Rewrote `findAboveLandmark` to be order-independent: for a purpose's column, it now looks at *every other* purpose in that column (not just ones with a smaller fixed index), finds whichever of them already exists, and returns whichever existing one currently has the **lowest** (furthest-down) rendered bottom edge (`logicalBox.y + logicalBox.height`) — i.e., the current bottom of that column's stack, however it got there. Applied uniformly to both columns (`[TITLE, SUBTITLE]` too), removing the fixed-order assumption entirely.

**Rationale**: This directly fixes the reported bug for any creation order within the upper-right cluster (Composer/Page number/Part have no inherent "primary" member — the original feature request even listed them as "PAGE, PART and COMPOSER," not composer-first) and is strictly more general than the sequence-based version it replaces: for the *expected* order (Title before Subtitle; Composer before Page/Part) it behaves identically to before, and for any other order it now stacks correctly instead of overlapping. It also removes an implicit, undocumented assumption (that `LANDMARK_COLUMNS`' array order was meaningful) that nothing else in the codebase actually relied on.

**Alternatives considered**: Keeping fixed-order stacking but treating Composer as "special" (never re-stacked, always base position) and instead re-flowing Page/Part to detect Composer specifically — rejected as more complex for no benefit over the general "stack below whichever else exists" rule, which handles the Composer-created-last case for free.

## 3. Menu wiring: the existing `subMenu` mechanism, following the `arpeggioMenuOption`/`arpeggioStyleOption` factory pattern exactly

**Finding**: `SuiConfiguredMenuOption.subMenu` (`src/ui/menus/menu.ts:147`) already exists and is already used by `arpeggioMenuOption`/`arpeggioStyleOptions` (`src/ui/menus/note.ts:53-75`) to show a fixed list of leaf choices as a nested menu level, with no new dialog or top-level menu registration. `menu.vue` (`src/ui/components/menus/menu.vue:36`) already filters each level's items through `item.display(props.menuStructure)`, recursively, so a leaf's `display` callback receives the same top-level `SuiMenuBase`-like object (with `.view`) as a top-level option would.

**Decision**: Add one parent option, `landmarkTextMenuOption`, to `SuiTextMenuOptions` in `src/ui/menus/text.ts`, with `subMenu: landmarkOptions` where `landmarkOptions: SuiConfiguredMenuOption[]` is built by a `landmarkOption(purpose, label, icon)` factory function, one call per purpose (Title, Subtitle, Composer, Copyright, Date, Page number, Part) — directly mirroring `arpeggioStyleOption`'s factory-function shape.

**Rationale**: No new submenu infrastructure needs to be built; this is the same mechanism the codebase already uses for exactly this kind of "one parent, several related leaf choices" menu, satisfying the spec's "submenu in the text menu" requirement with the lowest-risk, most consistent approach.

## 4. Page-number marker substitution requires zero new rendering code

**Finding**: `SmoTextGroup.getPagedTextGroups(tg, pages, pageHeight)` (`scoreText.ts:550-587`), called once per text group on every render pass (`scoreRender.ts:117`, `this.score!.layoutManager!.pageLayouts.length` as the page count), already has exactly two branches: `pagination === ONCE` (return the group unchanged, once) and everything else (duplicate the group once per page, and on each copy do `xx.text = xx.text.replace('###', (ix+1).toString())` and `xx.text = xx.text.replace('@@@', pages.toString())`). Critically, **the "everything else" branch does not currently distinguish EVERY from ODD/EVENT/SUBSEQUENT** — any non-ONCE pagination value gets the identical repeat-and-substitute treatment today.

**Decision**: Create PAGE landmarks with literal text `Page ### of @@@` and `pagination: EVERY` (set by `createLandmarkText`, research §2). No changes to `getPagedTextGroups`, `scoreRender.ts`, or any rendering file are needed — the existing per-page marker substitution mechanism already produces the correct "Page x of y" text on every page, confirmed by direct reading of the current implementation rather than assumed.

**Rationale**: De-risks FR-010 entirely at the data layer; this is the single biggest simplification this research uncovered. Reusing the exact marker syntax (`###`/`@@@`) the user specified also matches the "Insert Special" dropdown already offered inside the free-text editor for ordinary Score Text (`textBlock.vue:55-58`), so the landmark's authored text is not a new, parallel syntax.

**Alternatives considered**: Computing "Page x of y" once at creation time and hard-coding the numbers — rejected; the spec explicitly requires the numbers to stay correct as pages are added/removed (FR-010), which only the existing per-render substitution mechanism, not a one-time computation, can satisfy.

## 5. Content source resolution

**Decision**: A small `resolveLandmarkText(purpose, view): string` helper in `src/ui/menus/text.ts`:

- TITLE → `view.score.scoreInfo.title`
- SUBTITLE → `view.score.scoreInfo.subTitle`
- COMPOSER → `view.score.scoreInfo.composer`
- COPYRIGHT → `view.score.scoreInfo.copyright`
- DATE → today's date as `YYYY-MM-DD`, reusing the exact zero-padded format already used for the MusicXML export date (`src/smo/mxml/smoToXml.ts:109-111`, `today.getFullYear() + '-' + dd(today.getMonth()+1) + '-' + dd(today.getDate())`) rather than inventing a new date-formatting convention.
- PAGE → literal `Page ### of @@@` (research §4)
- PART → `view.score.staves[0].partInfo.partName`

**Rationale**: Reuses `SmoScoreInfo` fields and the existing `partInfo.partName` (`src/smo/data/partInfo.ts:160`) directly, per the spec's explicit sourcing rules; reuses an existing date-format convention instead of introducing a second one.

## 6. Existing-landmark lookup follows the same score/part storage routing `addTextGroup` already implements

**Finding**: `SuiScoreViewOperations.addTextGroup` (`src/render/sui/scoreViewOperations.ts:65-86`) already branches: when `isPartExposed() && score.staves[0].partInfo.preserveTextGroups`, a newly added text group is stored on `score.staves[0].partInfo.textGroups`; otherwise it's stored on `score.textGroups` (via `score.updateTextGroup`). This routing is pre-existing, generic behavior for all text groups (not landmark-specific) and is out of scope to change.

**Decision**: A `findLandmark(purpose, view): SmoTextGroup | undefined` helper checks the same collection `addTextGroup` would have written to: `(view.isPartExposed() && view.score.staves[0].partInfo.preserveTextGroups ? view.score.staves[0].partInfo.textGroups : view.score.getTextGroups()).find(tg => tg.purpose === purpose)`.

**Rationale**: Guarantees "does this landmark already exist" and "where would a new one be stored" always agree, without introducing a second, parallel notion of text-group storage.

## 7. Menu-item visibility

**Decision**: Two small predicates in `src/ui/menus/text.ts`:

- `sourceTextDefined(purpose, view)`: for TITLE/SUBTITLE/COMPOSER/COPYRIGHT, `view.score.scoreInfo.<field>.trim() !== ''`; for DATE and PAGE, always `true` (spec FR-004); for PART, `view.isPartExposed()` (spec FR-003).
- Each leaf's `display`: `sourceTextDefined(purpose, menu.view) || (purpose !== PART_PURPOSE && !!findLandmark(purpose, menu.view))`.

The `OR` with "already exists" (for every purpose except Part) implements the spec's edge case that an already-created landmark's menu entry must stay available even if its source score field is later cleared. Part is deliberately excluded from that `OR`: per spec User Story 2 Scenario 2, the Part entry must track the *current view's* exposed/not-exposed state, not whether a Part landmark happens to already exist somewhere.

**Rationale**: Directly implements spec FR-002/FR-003/FR-004 and the corresponding Edge Cases without adding any new stored flag — visibility is entirely computed from existing score/part/view state plus the `findLandmark` lookup from research §6.

## 8. Dialog gating (no free-text editing, no pagination-type control) is driven by `purpose`, and a freshly created landmark must skip the dialog's "first open starts in text-editing mode" default

**Finding**: `textBlock.vue` (`src/ui/components/dialogs/textBlock.vue:27-31`) decides its initial `DialogMode` from `props.modifier.value.edited`: `false` → starts in `'editing'` (the free-text/tiptap session), which is how a brand-new, blank "Score Text" gets its first typing session. `edited` is a plain, intentionally non-persisted (`scoreText.ts:509`, "indicates not edited this session") class field — not in `nonTextAttributes` — so it is never written to saved JSON, but it *is* preserved on the live object across a dialog's `commitCb` → `view.updateTextGroup(modifier.value)` → `score.updateTextGroup` round trip, because that path pushes the same in-memory object into the score's `textGroups` array rather than a serialized-and-reconstructed copy. The dialog also gates two other things purely on UI, not data: the "Edit Text" pencil button that's the *only* way to enter `'editing'` mode (`textBlock.vue:177-179`), and the "Page Behavior" `selectComp` (`textBlock.vue:198-204`), both always rendered today for every text group regardless of purpose.

**Decision**: Three changes, all in `textBlock.vue`, all conditioned on a single `const isLandmark = props.modifier.value.purpose !== SmoTextGroup.purposes.NONE`:
1. Hide the "Edit Text" button when `isLandmark` (leaving "Move" as the only idle-mode action button for a landmark) — this satisfies FR-013 by removing the only *manual* entry point into the tiptap editing session, with no change needed to `textGroupEditor.vue` itself.
2. Hide the "Page Behavior" row when `isLandmark` — satisfies FR-014.
3. **Fold `isLandmark` into the initial-`mode` computation itself**: `ref((props.modifier.value.edited || isLandmark) ? 'idle' : 'editing')`, instead of `ref(props.modifier.value.edited ? 'idle' : 'editing')`. This is the change that actually matters for correctness, and was caught only after the first pass of this feature shipped `isLandmark` as a template-only gate: hiding the *button* stops a user from manually re-entering `'editing'`, but does nothing about the dialog's own *initial* mode, which is computed from `edited` alone, independent of the button. Any text group whose `purpose !== NONE` but whose `edited` field happens to be `false` — which includes every MusicXML-imported Title/Subtitle/Composer group (`xmlToSmo.ts:136-148`, via `createTextForLayout`, research §1) now that `purpose` is a real field, not just ones created by this feature's own `createLandmarkText` — would otherwise still boot straight into the free-text tiptap session on first open, contradicting FR-013 for exactly the scores this feature is most likely to be used on (ones with import-derived Title/Subtitle/Composer text already present). Folding the check into `mode`'s own initial value closes that gap for every landmark-purpose group, regardless of how or when it was created, not only ones built via `createLandmarkText`.

Because `mode`'s initialization now guarantees `'idle'` for any `purpose !== NONE` group, `SmoTextGroup.createLandmarkText` (research §2) no longer needs to set `edited: true` on the group it returns — that line has been removed as redundant; `purpose` alone is now sufficient signal.

**Rationale**: `purpose` (now a real field per research §1) is the one signal that already means "this text group's content is derived, not freely typed," so gating both UI affordances *and* the initial mode off it in one place (rather than partly off `purpose` and partly off a data-layer `edited: true` side effect scoped only to `createLandmarkText`) keeps the guarantee "a landmark never shows its text editor" true for every landmark-purpose group the dialog might ever open, including ones this feature didn't create.

**Alternatives considered**: A dedicated boolean like `noFreeTextEdit`, or leaving the fix as "set `edited: true` in `createLandmarkText`" (the original, incomplete first pass) — both rejected: the former is redundant with `purpose !== NONE`; the latter only covers groups created through this feature's own code path and silently fails for any purpose-tagged group created another way (MusicXML import today; potentially others later).

## 9. No changes needed to `textBlockVue.ts` or the create-vs-open control flow

**Finding**: `SuiTextBlockDialogVue` (`src/ui/dialogs/textBlockVue.ts:17-127`) already has two branches: `!parameters.modifier` (build a blank group, add it to the view, then open) and `else` (an existing, already-in-the-score group is passed in — `deserializePreserveId` it into a working copy, mark `beingEdited`, open). A menu handler that (a) looks up an existing landmark via `findLandmark`, (b) if none, builds one via `createLandmarkText` and calls `view.addTextGroup(group)` itself, then (c) always calls `SuiTextBlockDialogVue({ ..., modifier: group })`, lands in the `else` branch in both the "just created" and "already existed" cases — which is exactly the desired behavior (FR-005/FR-006/FR-017) with no modification to this file.

**Decision**: Implement the landmark handler entirely in `src/ui/menus/text.ts`; leave `textBlockVue.ts` untouched.

**Rationale**: Minimizes surface area changed and reuses proven, already-working dialog bootstrap code.

## 10. Testing approach
