# Phase 0 Research: Lyric Editor Live Preview and Position Cursor

All unknowns below were resolved by reading the existing codebase (no external research was needed). No `NEEDS CLARIFICATION` markers remain in the Technical Context.

## 1. Drawing a marker directly into the score's SVG

- **Finding**: Two existing, unrelated features already draw/remove small transient SVG overlay elements directly against a page's render context, confirming the pattern and coordinate convention to follow:
  - `SvgHelpers.renderCursor(svg, x, y, height)` (`src/render/sui/svgHelpers.ts:195`) draws a small I-beam-shaped cursor glyph as a raw `<path>`, appended via `svg.appendChild(e)`. Used by the legacy `SuiInlineText.renderCursorAt()` (`src/render/sui/textRender.ts:370`), which computes `x`/`y` relative to the render context's box (`x = this.startX - this.context.box.x`, etc.) before calling it, and removes it via a `$('svg #inlineCursor').remove()` selector on a wrapping group.
  - `NoteEntryCaret` (`src/render/sui/NoteEntryCaret.ts`) — a different, currently-shipping feature (the note-entry-mode pitch caret) — resolves its render context the same way (`this.tracker.renderer.pageMap.getRenderer(pageBox)`, an `SvgPage`), and appends/removes its own raw SVG elements directly against `this.context.svg` (`SvgPage.svg`, a `get svg(): SVGSVGElement`, `src/render/sui/svgPageMap.ts:381`) and `this.context.box` (`src/render/sui/svgPageMap.ts:211`), e.g. `this.context.svg.insertBefore(cursorRectangleElement, this.context.svg.firstChild)` and `this.cursorRectangleElement.remove()` on cleanup.
- **Decision**: Follow the `NoteEntryCaret` pattern (the more current of the two): resolve `const context = view.renderer.pageMap.getRenderer({ x, y })`, and if non-null, draw directly against `context.svg`, offsetting coordinates by `context.box.x`/`context.box.y`. Track the returned element and call `.remove()` on it directly for cleanup (no jQuery selector needed, since the reference is held).
- **Rationale**: This is the actively-used, non-legacy pattern for exactly this kind of "small transient overlay tied to a note's position" need, and avoids any dependency on `SuiInlineText`/`SuiLyricEditor`, which `010-vue-lyric-dialog` deliberately stopped using.
- **Alternatives considered**: Reviving `SuiLyricEditor`'s `startCursorPromise()`/blink-polling cursor — rejected; that machinery exists to drive a full editable-in-SVG text run (glyph-by-glyph layout, blinking via a 333ms polling promise), none of which this feature needs for a single static position marker. An HTML-overlay `<div>` positioned via `pageMap.svgToClient()` instead of drawing into the SVG itself — rejected; it would need its own scroll/zoom-resync logic that drawing directly into the SVG gets for free (it scrolls/zooms with the rest of the notation).

## 2. Marker shape

- **Finding**: `SvgHelpers.renderCursor` draws an ornate, curved I-beam glyph (quadratic-curve path, `stroke:#555`) — styled for a real text-editing caret. The feature description explicitly asks for "a subtle cursor (vertical line)."
- **Decision**: Add a new, additive static method, `SvgHelpers.renderLyricPositionMarker(svg: SVGSVGElement, x: number, y: number, height: number): SVGLineElement`, drawing a single plain `<line>` (`x1=x2=x`, `y1=y`, `y2=y+height`), thin stroke width, a low-opacity/muted color, and returning the created element so the caller can remove it later. `SvgHelpers.renderCursor` itself is left unchanged.
- **Rationale**: A plain vertical line is simpler and more literally "subtle" than the existing glyph cursor, and matches the spec's Assumption ("a thin vertical line resembling a text caret... not a highlighted box or a bright/attention-grabbing color"). Returning the element (unlike `renderCursor`, which returns `void`) is a deliberate, non-breaking addition specific to the new method — no existing caller of `renderCursor` is affected.
- **Alternatives considered**: Reusing `renderCursor` as-is — rejected only because its specific glyph shape is more visually prominent than "a subtle... vertical line" calls for; the underlying draw/track/remove pattern is otherwise identical.

## 3. Computing the marker's position

- **Finding**: `SmoLyric` gets a `logicalBox` populated by the renderer once it has been rendered at least once (referenced by the legacy `SuiLyricSession._startSessionForNote()`, `src/render/sui/textEdit.ts:1212-1215`: `if (this.lyric.logicalBox !== null) { startX = this.lyric.logicalBox.x; startY = ...}`). A note being edited already has an ambient, already-rendered score (including any pre-existing lyric) before the dialog opens, so `currentLyric.value.logicalBox` (`lyric.vue`'s existing `currentLyric` ref from `010-vue-lyric-dialog`) is already populated whenever the current note has existing text for the active verse. `SmoNote.logicalBox` is likewise already populated for any rendered note. `SmoScoreText.fontPointSize(size)` (`src/smo/data/scoreText.ts:79`, already used by `lyricEditor.vue`) converts a lyric's font size to a usable point size for a marker height.
- **Decision**:
  - If `currentLyric.value.logicalBox` is set (existing text), position the marker at its bounding box's right/bottom edge: `x = logicalBox.x + logicalBox.width`, `y = logicalBox.y`, `height = logicalBox.height`. This approximates "end of the existing text" using the whole rendered text run's box rather than per-character glyph metrics (which are not available without the block-layout machinery `010` deliberately dropped).
  - Otherwise (no rendered lyric yet), position the marker near the note, mirroring the legacy fallback: `x = note.logicalBox.x`, `y = note.logicalBox.y + note.logicalBox.height + SmoScoreText.fontPointSize(currentLyric.value.fontInfo.size)`, with a height equal to `SmoScoreText.fontPointSize(...)`.
- **Rationale**: Directly satisfies FR-002/FR-003 with data already available on the existing `currentLyric`/note objects — no new score-model reads, no per-character layout work.
- **Alternatives considered**: Computing exact end-of-text-run pixel position via glyph metrics — rejected as out of scope; the spec calls for a "subtle" marker, not pixel-perfect caret placement, and this would require reintroducing the block-layout machinery `010` removed.

## 4. When to (re)position and remove the marker

- **Decision**: In `lyric.vue`:
  - Recompute and redraw the marker every time `loadNote()` runs (dialog open, and after every navigate/delete) — immediate, not debounced, since it reflects a definite state change (a different note/verse is now current).
  - Recompute and redraw the marker again after every debounced preview write (§5) completes, so it keeps following the growing text on the *same* note during a longer typing pause without waiting for the next navigation.
  - Remove the marker (and clear the tracked element reference) when `mode` changes to `'dialog'` (`enterDialogMode()`) and when the dialog finishes (`finish()`, both OK and Cancel), plus on component unmount as a safety net.
- **Rationale**: Directly satisfies FR-004/FR-005 using the same points in the component's lifecycle that `010`/`011` already hook into (`loadNote`, `navigate`, `enterDialogMode`, `finish`) — no new state machine, just an added side effect at each of those existing points.

## 5. Periodic in-progress text preview

- **Finding**: `textGroupEditor.vue` (`009-text-editor-live-preview`) already implements exactly this shape of feature for the text-block dialog: `useEditor({ ..., onUpdate: schedulePreview, ... })`, where `schedulePreview()` clears/resets a `setTimeout` on every edit and `pushPreview()` (run only after a `PREVIEW_DEBOUNCE_MS = 400` quiet period) reads the current document and calls `props.rerender()`, which the parent wires to the real score-update call (`view.updateTextGroup(...)`).
- **Decision**: Add the identical pattern to `lyricEditor.vue`: `useEditor({ ..., onUpdate: schedulePreview, ... })`, with `schedulePreview`/`pushPreview` implemented locally using the same 400ms debounce, where `pushPreview()` simply does `emit('preview')` (no payload — `lyric.vue` already has a ref to pull `getText()` from, via the existing `lyricEditorRef`). `lyric.vue` adds `@preview="onEditorPreview"` next to the existing `@advance="onEditorAdvance"` binding on `<lyricEditorComp>`, and `onEditorAdvance` is implemented as `await commitIfChanged(); updateMarker();` — reusing `010`'s existing `commitIfChanged()` (which already only writes when text actually changed) completely unchanged, then repositioning the marker per §4.
- **Rationale**: `commitIfChanged()`'s write (`view.addOrUpdateLyric`) *is* the score update the preview needs to show — there is no separate "draft" concept anywhere else in this dialog's architecture (established in `010`/`011`: every edit is already committed incrementally, with no whole-session undo). Reusing it verbatim means the periodic preview and the eventual real persisted state are, by construction, never out of sync (FR-009) — they're the same write, just also triggered while the user pauses mid-typing, not only on navigate/finish.
- **Alternatives considered**: A separate, parallel "preview-only" render path that doesn't touch the real `SmoLyric`/score model — rejected: it would require inventing a second, temporary rendering mechanism the rest of this dialog has no equivalent of, contradicting the "no new draft/undo state" framing in FR-009 and adding real complexity for no behavioral benefit (nothing in this dialog's design distinguishes "preview" from "real" once written — see `010-vue-lyric-dialog` research.md §8's identical reasoning for why OK/Cancel are already the same operation here).

## 6. Interaction with `011-lyric-editor-auto-advance`

- **Finding**: `011` already added an `advance` emit and its own keyboard-shortcut extension entries (`-`, `Space`) to `lyricEditor.vue`, alongside the pre-existing `Enter`/`Shift-Enter` suppression.
- **Decision**: The new `onUpdate: schedulePreview` hook and the `advance` emit are independent and additive — TipTap's `onUpdate` fires for every document change regardless of what triggered it (typed character, or the `-` key's own `insertContent('-')` call from `011`), so hyphen insertion also schedules a preview tick with no extra wiring. Space never inserts anything, so it does not by itself trigger a new `onUpdate` (though the resulting navigation via `onEditorAdvance` already repositions the marker immediately per §4).
- **Rationale**: No changes needed to `011`'s existing `'-'`/`'Space'` shortcut entries; the two features compose without interaction.
